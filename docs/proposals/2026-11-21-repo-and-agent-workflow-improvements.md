# Proposal: Элегантная, быстрая и эффективная работа облачного агента с локальной машиной и Git-репозиториями

- **Статус**: Draft / Proposal
- **Дата**: 2026-11-21
- **Версия базы кода на момент анализа**: `0.21.0`
- **Ограничения архитектуры проекта**: Zero runtime dependencies в Node.js (`src/*.mjs`), stdlib-only в Python, сохранение строгих границ безопасности (`checkPath`, `protected`, `timingSafeEqual`).

---

## 1. Резюме (Executive Summary)

На сегодняшний день `arena-bridge` отлично решает задачу предоставления облачному агенту (в изолированной песочнице с выходом в интернет) доступа к файлам, терминалу, браузеру и macOS-десктопу через HTTP/MCP-туннель. После удаления гейта подтверждений и окна доверия в `0.21.0` главный барьер взаимодействия переместился из плоскости *разрешений* в плоскость **сетевой латентности (RTT через туннель), расхода контекстного окна LLM и избыточности низкоуровневых операций при работе с кодом и Git**.

Когда облачный агент работает с репозиторием на вашем компьютере сейчас, он вынужден выбирать из двух крайностей:
1. **Работать удалённо по одному файлу через HTTP (`POST /call`)**: десятки последовательных запросов `list_dir` → `search_files` → `read_file` → `edit_file` → `bash (git status/diff/test)`. Каждый шаг стоит 100–400 мс на туннель + целый turn генерации LLM, а чтение больших файлов целиком сжигает контекст.
2. **Клонировать репозиторий с GitHub в облачную песочницу**: агент теряет ваши локальные незакоммиченные правки, `.env`-файлы (которые не в Git), локальные ветки, кеши сборок и доступ к локальному окружению (macOS SDK / Xcode / локальные сервисы), а синхронизация обратно превращается в череду лишних коммитов в `main` или ручную переброску архивов.

Ключевой архитектурный прорыв для `arena-bridge` — **превратить мост из простого «удалённого вызова процедур по файлам» в полноценный Git-aware и Repo-aware шлюз**, позволяющий агенту:
- мгновенно ориентироваться в ваших локальных репозиториях одним запросом;
- **клонировать и пушить напрямую в ваш локальный репозиторий через сам мост** (Git Smart HTTP поверх существующего туннеля — без GitHub-посредника и грязных WIP-коммитов);
- выполнять чтение диапазонов строк, мульти-правки и батч-запросы за 1 RTT;
- искать по коду со скоростью `git grep` / `ripgrep` с учётом `.gitignore`.

Ниже разобраны узкие места текущей реализации (`src/catalog.mjs`, `src/direct.mjs`, `src/hub.mjs`, `src/device.mjs`, `src/prompt.mjs`) и предложен поэтапный план улучшений без нарушения принципа **zero dependencies**.

## 2. Диагностика текущих узких мест (на основе анализа кода)

### 2.1. Отсутствие нативного Git-транспорта и Git-примитивов
- Сейчас агент в облаке имеет быстрый локальный SSD в своей песочнице (где у него работают мгновенные `grep`, LSP, параллельное чтение, локальные тесты), но репозиторий живёт на вашем Mac.
- Чтобы синхронизировать код между песочницей агента и вашим Mac без пуша сырых веток в удалённый GitHub, агенту приходится гонять `tar.gz` через `file_get`/`file_put` (лимит 16 МБ, base64-оверхед +33%) или писать изменения пофайлово по сети.
- Нет единого инструмента, который за один вызов отдаёт агенту полный контекст рабочей копии (`branch`, `ahead/behind`, `staged/unstaged/untracked`, `stash`, последние коммиты). Агент тратит 3–5 вызовов `bash` на разведку в каждом репозитории.

### 2.2. Примитивные файловые операции для больших кодовых баз (`src/catalog.mjs`)
1. **`read_file` читает только с байта `0` (`src/catalog.mjs:58-85`)**:
   - Есть только `max_bytes`, но нет `offset_line` / `limit_lines` и нумерации строк. Если файл весит 250 КБ (например, крупный модуль или лог), агент либо скачивает весь файл в контекст LLM, либо получает обрезанный по байтам кусок без возможности прочитать строки `800..950`.
2. **`edit_file` делает только одну замену в одном файле (`src/catalog.mjs:116-149`)**:
   - Рефакторинг из 6 правок в 3 файлах требует 6 отдельных HTTP-запросов и 6 шагов агента. Нет `multi_edit` (несколько блоков в одном файле атомарно) и нет `apply_patch` (применение unified diff к нескольким файлам сразу с `git apply --check`).
3. **`search_files` обходит дерево в JS и игнорирует `.gitignore` (`src/catalog.mjs:221-284`)**:
   - Пропускается фиксированный список `skipDirs` (`node_modules`, `.git`, `.venv`, `dist`, `build`, `.next`), но директории вроде `target/` (Rust), `.DerivedData/` / `.build/` (Swift/Xcode), `vendor/`, `.turbo/`, `coverage/`, большие `.map` или сгенерированные бандлы читаются в память целиком через `fsp.readFile(full, 'utf8')`.
   - На крупном монорепозитории это медленно и забивает выдачу мусором, хотя на машине почти всегда есть `git grep` (внутри репо) или `rg` (`ripgrep`), работающие на порядки быстрее и строго уважающие `.gitignore`.
4. **`list_dir` не учитывает `.gitignore` и делает покомпонентный `lstatSync` на каждый элемент**:
   - В `src/policy.mjs:6-74` `resolveTarget` выполняет серию синхронных `fs.lstatSync` / `fs.realpathSync` вверх по дереву, а `checkPath` (`src/policy.mjs:100`) на **каждый** файл в `list_dir` и `search_files` заново резолвит все 17 путей из `cfg.protected` через файловую систему! При обходе 2 000 файлов это `2 000 × 18 = 36 000` синхронных системных вызовов в event loop.

### 2.3. Накладные расходы протокола и транспорта
1. **Нет пакетного вызова (`POST /batch`) и HTTP-сжатия**:
   - Когда агенту нужно прочитать 8 файлов и проверить `git status`, он делает 9 HTTP-вызовов через `curl` (каждый раз новый TLS handshake к туннелю Cloudflare/ngrok).
   - Ответы `sendJson` / `sendRaw` (`src/http.mjs`) не сжимаются `gzip`/`br` (встроенный `node:zlib`), хотя JSON-деревья, логи и исходники сжимаются в 5–10 раз.
2. **Оверхед процесса `curl` в песочнице агента**:
   - В промпте (`src/prompt.mjs:24-29`) агенту предлагается вызывать мост сырым `curl -sS -X POST ... -d '{"tool":...}'`. При передаче многострочного кода или кавычек в `write_file`/`edit_file`/`bash` через bash+curl агенты регулярно ошибаются в экранировании JSON и тратят попытки на `INVALID_JSON`.
3. **Задержка и урезанный каталог в Hub-режиме (`src/device.mjs`, `src/hub.mjs`)**:
   - В `src/device.mjs:50-60` устройство опрашивает хаб коротким поллингом: при `204` спит `700 ms`. Каждая команда агента искусственно тормозит в среднем на ~350–700 мс просто на ожидании следующего тика поллинга, хотя long-polling (удержание запроса 25 с на хабе) или WebSocket (`src/ws.mjs` уже написан!) снижает задержку до ~0 мс.
   - В `src/hub.mjs:85` `listTools` отдаёт только `toolCatalog()` (16 базовых инструментов), теряя `browser`, `mac` и `telegram` инструменты подключённого устройства.

## 3. Предлагаемые улучшения (Architecture & Feature Proposal)

Предложения сгруппированы по 5 направлениям — от самых трансформационных для работы с репозиториями до транспортных оптимизаций.

---

### Направление A. Мост как нативный Git-шлюз (Git Smart HTTP + Repo Worktrees)

Это **главная фича**, которая делает работу облачного агента с репозиториями на вашем компьютере по-настоящему элегантной.

#### A1. Git Smart HTTP поверх `arena-bridge` (`/git/<repo-alias>.git/...`)
Встроить проксирование стандартного `git http-backend` (он поставляется вместе с Git на macOS и Linux из коробки, **0 внешних зависимостей**).

**Как это работает:**
1. Мост публикует маршрут `/git/<repo>/*`, защищённый тем же `Authorization: Bearer <token>` (в Git это передаётся штатно через `git -c http.extraHeader="Authorization: Bearer $ARENA_BRIDGE_TOKEN"`).
2. Облачный агент в своей быстрой Linux-песочнице делает одну команду:
   ```bash
   git -c http.extraHeader="Authorization: Bearer $ARENA_BRIDGE_TOKEN" \
     clone "$ARENA_BRIDGE_URL/git/my-project" /home/user/webapp
   ```
3. Агент работает со всей скоростью локального SSD песочницы: редактирует десятки файлов, гоняет линтеры/тесты, делает аккуратные коммиты и пушит в выделенную ветку прямо на ваш Mac:
   ```bash
   git push origin HEAD:refs/heads/agent/fix-auth
   ```
4. **Безопасность вашей рабочей копии**: мост принимает `git push` только в namespace `refs/heads/agent/*` (или с `receive.denyCurrentBranch=updateInstead` только для отдельных worktree), **никогда не перезаписывая вашу текущую ветку и незакоммиченные файлы**.

**Что это даёт:**
- Скорость клонирования и синхронизации — на уровне бинарного pack-протокола Git (дельта-сжатие, доли секунды на инкрементальный `fetch`/`push`).
- Никаких мусорных коммитов на GitHub ради того, чтобы перекинуть код с ноутбука в облако и обратно.
- Работает даже с полностью локальными репозиториями, у которых вообще нет remote на GitHub/GitLab.
- На Mac вы сразу видите ветку `agent/fix-auth` в своём IDE (Cursor / VS Code / Xcode / Fork), смотрите чистый diff и вливаете одной кнопкой.

#### A2. Управление изолированными `git worktree` для агента (`repo_worktree_*`)
Когда вы сами пишете код в `~/projects/app`, а агент параллельно правит файлы или запускает сборку в той же папке — возникает конфликт индексов, прыгающие ветки и сломанный dev-сервер.

Предлагается инструмент `git_worktree`:
- `action: "create"` — создаёт лёгкий worktree в `~/.arena-bridge/worktrees/<repo>/<task>` (или рядом с проектом) на базе вашего текущего `HEAD` (опционально копируя локальный uncommitted diff и симлинкуя безопасные кеши/зависимости по конфигу, например `node_modules` при совпадении lock-файла).
- Агент может запускать сборку, `xcodebuild`, `pytest` или `npm test` на вашем Mac в этом worktree через `bash`, **вообще не трогая файлы в вашем открытом редакторе**.
- `action: "cleanup"` — удаляет временный worktree после завершения задачи, оставляя ветку в основном репозитории.

### Направление B. Реестр проектов и мгновенный «слепок репозитория» (Repo Discovery & Context)

Сейчас агент не знает, где на вашем Mac лежат проекты (`~/projects`, `~/work`, `~/Developer` и т.д.), и тратит первые 5–10 запросов на поиск папки и выяснение состояния репозитория.

#### B1. Автоматический каталог репозиториев (`repos_list`)
- В конфиге задаётся `workspaceDirs: ["~/projects", "~/Developer"]` (или используется существующее поле `roots`, которое сейчас простаивает как legacy!).
- Инструмент `repos_list` быстро сканирует верхние 1–3 уровня этих директорий на наличие `.git` и возвращает компактный реестр:
  ```json
  {
    "repos": [
      {
        "alias": "arena-bridge",
        "path": "/Users/alex/projects/arena-bridge",
        "branch": "main",
        "dirty": true,
        "remote": "git@github.com:vernikr/arena-bridge.git",
        "last_commit": "fdd0d41 fix: mark bin/arena-bridge.mjs and install.sh executable"
      }
    ]
  }
  ```
- Когда вы пишете агенту в чате *«почини баг с иконкой в проекте foo»*, агент за **один вызов** находит точный путь `/Users/.../foo`, видит активную ветку и статус.

#### B2. Единый инструмент `repo_overview` / `git_status` (1 RTT вместо 6)
Один легковесный read-only инструмент, возвращающий за 1 запрос всю картину репозитория:
- Текущая ветка, upstream, `ahead`/`behind`, наличие конфликтов/rebase/merge;
- Staged / unstaged / untracked файлы со статистикой (`--numstat`);
- Список `git stash`;
- Последние `N` коммитов (`oneline`);
- Дерево файлов репозитория через `git ls-files` (мгновенно, уже отфильтровано по `.gitignore`, без `node_modules` и мусора) + топ-уровень конфигурационных файлов (`package.json`, `pyproject.toml`, `Cargo.toml`, `Package.swift`, `AGENTS.md`, `CLAUDE.md`).

#### B3. Структурированный `git_diff` с пагинацией и фильтрами
Инструмент `git_diff` (`staged`, `base_ref`, `paths`, `context_lines`, `stat_only`), который возвращает аккуратно отформатированный diff без риска переполнить лимит вывода на огромных lock-файлах (`package-lock.json`, `Podfile.lock` автоматически сворачиваются в summary, если не запрошены явно).

### Направление C. Хирургические файловые и кодовые инструменты (Token & Turn Efficiency)

Если агент работает напрямую с файлами на Mac (например, нужно быстро поправить 2 файла и прогнать `swift build`), инструменты должны быть максимально экономными к токенам и числу шагов:

#### C1. Диапазонное чтение в `read_file` + мульти-чтение `read_files`
- Добавить в `read_file` параметры:
  - `offset_line` (1-based) и `limit_lines` (например, строки 120–220);
  - `with_line_numbers: boolean` — отдавать строки в формате `120\t...`, чтобы агент не ошибался при анализе больших файлов;
  - метаданные `total_lines`, `mtime_ms` и `sha256` (короткий хеш файла).
- Добавить `read_files` (`paths: [...]`) — чтение сразу 5–20 файлов за **один** HTTP-запрос.

#### C2. `apply_patch` и `multi_edit` с защитой от гонок (`expected_sha256` / `mtime`)
- **`multi_edit`**: массив замен `[{ old_text, new_text, replace_all }]` внутри одного файла или набора файлов. Применяется **транзакционно** (если хотя бы один блок не нашёлся — ни один файл не меняется, возвращается точная диагностика по индексу правки).
- **`apply_patch`**: принимает стандартный unified diff (один или многофайловый), валидирует все целевые пути через `checkPath(..., { write: true })` (чтобы патч не мог выйти в `protected` или обойти симлинки) и применяет через `git apply --3way` или встроенный парсер hunk'ов.
- **Защита от перезаписи ваших правок (Optimistic Concurrency)**: если вы одновременно правите тот же файл в редакторе на Mac, опциональное поле `if_match_sha` предотвращает тихое затирание ваших свежих изменений агентом (вернёт `CONFLICT` со свежим диффом).

#### C3. Быстрый `code_search` на базе `git grep` / `rg` с fallback на Node
- Модернизировать `search_files`:
  1. Если установлена утилита `rg` (`ripgrep`) или целевая папка внутри Git-репозитория (`git grep -n -I --untracked`), использовать их для поиска (с обязательной пост-фильтрацией найденных путей через закешированный `checkPath`, чтобы никогда не раскрыть `protected`-пути).
  2. Добавить параметры `glob` / `include` (например, `"*.swift"`), `context_lines` (`-C 2`, чтобы агент сразу видел контекст функции без лишнего `read_file`) и `respect_gitignore: true` (по умолчанию).
  3. Оставить текущий JS-обход как надёжный fallback для папок вне Git при отсутствии `rg`.
- Результат: ускорение поиска на больших проектах с секунд до **5–20 мс** и чистая выдача без артефактов сборки.

#### C4. Кеширование `resolveConfigured(cfg.protected)` в рамках одного вызова
- В `src/policy.mjs` резолвить список `cfg.protected` **один раз на запрос** (передавая предвычисленный массив `resolvedProtected` в `checkPath` при обходах `list_dir` и `search_files`), а не на каждый файл. Это убирает десятки тысяч лишних `lstatSync` и ускоряет `list_dir(recursive: true)` в 10–15 раз без малейшего ослабления безопасности.

### Направление D. Ускорение транспорта и SDK-скрипт для песочницы агента

#### D1. Пакетный эндпоинт `POST /batch` (Pipeline Execution)
Добавить эндпоинт `POST /batch`:
```json
{
  "stop_on_error": true,
  "calls": [
    { "tool": "read_file", "args": { "path": "~/projects/app/src/a.ts" } },
    { "tool": "read_file", "args": { "path": "~/projects/app/src/b.ts" } },
    { "tool": "bash", "args": { "command": "git status -sb", "cwd": "~/projects/app" } }
  ]
}
```
- Выполняет независимые read-вызовы параллельно (или последовательно с `stop_on_error: true` для мутаций) за **1 сетевой RTT** через туннель.
- Каждая операция внутри батча логируется в `audit.log` отдельной записью с общим `batch_id` — полная прозрачность в macOS-приложении сохраняется.

#### D2. Bootstrap CLI (`ab`) одной строкой в `GET /prompt`
Сейчас промпт учит агента конструировать `curl` с ручным JSON-экранированием. Элегантнее отдавать с самого моста маленький zero-dep клиент (`GET /client.mjs` или `GET /ab` — shell/node обёртка на ~80 строк), а в промпте давать одну строку инициализации:
```bash
export ARENA_BRIDGE_URL="https://..." ARENA_BRIDGE_TOKEN="..."
curl -fsSL -H "Authorization: Bearer $ARENA_BRIDGE_TOKEN" "$ARENA_BRIDGE_URL/ab" -o /usr/local/bin/ab && chmod +x /usr/local/bin/ab
```
После этого агент в песочнице работает лаконично, быстро и **без единой ошибки JSON-экранирования**:
```bash
ab repos                                  # список локальных репозиториев на Mac
ab clone my-repo /home/user/webapp        # клонировать репо с Mac в песочницу по Smart HTTP
ab git my-repo status                     # мгновенный обзор рабочей копии на Mac
ab read ~/projects/my-repo/src/app.mjs:1-120
ab exec --cwd ~/projects/my-repo "npm test"
ab sync-branch my-repo agent/feature-x    # запушить ветку из песочницы обратно на Mac
```
Такой CLI кроме того переиспользует HTTP Keep-Alive соединения (в случае батчей или демона сокета в песочнице) и автоматически распаковывает `gzip`.

#### D3. HTTP Compression (`gzip` / `br`) + Long-Polling / WS для Hub-режима
1. **Сжатие ответов (`node:zlib`)**: если клиент присылает `Accept-Encoding: br, gzip` и тело ответа > 1 КБ (`GET /tools`, `read_file`, `search_files`, `git_diff`, `chrome_snapshot`), сжимать ответ. Объём передаваемых по туннелю текстовых данных падает на 80–90%.
2. **Устранение задержки 700 мс в Hub-режиме (`src/device.mjs` + `src/hub.mjs`)**:
   - Перевести `POST /device/poll` на **long-polling** (хаб держит запрос до 25 с и мгновенно отвечает, как только в `queues.get(device)` появляется задача) либо на постоянный исходящий WebSocket (класс `WebSocketClient` в `src/ws.mjs` уже реализован в проекте!).
   - При регистрации/поллинге устройство передаёт свой `engine.mcpTools()` на хаб, чтобы `GET /tools` и `/mcp` на хабе видели полный набор инструментов устройства (включая `mac_*`, `chrome_*`, `telegram_*`), а не только 16 базовых.

### Направление E. Git-safety и UX разработчика на macOS

Поскольку в `0.21.0` гейт подтверждений убран («если служба запущена — всё разрешено»), при активной работе агента с репозиториями возрастает риск **случайных деструктивных Git-команд** (не злого умысла, а ошибки модели).

#### E1. Мягкий предохранитель для разрушительных Git-операций (Git Guardrails)
Без возврата старого назойливого гейта подтверждений на каждый чих, ввести настраиваемую защиту от необратимой потери незакоммиченного кода:
- Автоматический **pre-agent snapshot** (опционально): перед первой записью агента в «грязный» репозиторий за сессию мост может тихо сохранять слепок рабочего дерева через `git stash create` (это создаёт commit-объект в `.git/objects` **без изменения рабочих файлов и индекса!**) и записывать его SHA в `audit.log`.
- Если агент случайно испортил незакоммиченные файлы или сделал неудачный рефакторинг, вы в один клик в macOS-приложении (или командой `arena-bridge undo <entry-id>`) откатываете состояние к точному SHA до вмешательства агента!
- Блокировка (или требование явного флага) для команд вида `git push --force` в `main`/`master` и `git reset --hard` / `git clean -fdx` при наличии несохранённого stash-слепка.

#### E2. Карточка «Активные репозитории и ветки агента» в macOS App / CLI
- В `arena-bridge status` и в окне macOS-приложения показывать компактную строку: с каким репозиторием сейчас работает агент, какую ветку `agent/*` он обновил и кнопку «Copy `git diff main..agent/...`» / «Open in Editor».

## 5. Предлагаемая дорожная карта (Phased Roadmap)

Все этапы спроектированы так, чтобы **не добавлять внешних npm-зависимостей** (используются только встроенные модули Node.js `node:zlib`, `node:child_process`, `node:crypto`, `node:fs` и системный `git`).

### Фаза 1 — Быстрые победы (Impact: High, Effort: S — 1–2 дня)
1. **Оптимизация `policy.mjs` и `search_files`**: предвычисление `protected`-путей на один запрос; интеграция `git grep` / `rg` с fallback на JS и поддержкой `glob` + `context_lines`.
2. **Улучшение `read_file` и `multi_edit`**: поддержка `offset_line`, `limit_lines`, `with_line_numbers`, `sha256`, а также инструмента `read_files` (батч-чтение) и `multi_edit`.
3. **Инструменты `repos_list` и `repo_overview`**: автообнаружение локальных Git-репозиториев (переиспользование поля `roots` / `workspaceDirs` как списка папок с проектами) и сводка состояния репозитория за 1 вызов.
4. **HTTP `gzip`/`br` сжатие** в `src/http.mjs` + эндпоинт **`POST /batch`**.

### Фаза 2 — Нативный Git-мост и CLI-клиент агента (Impact: Very High, Effort: M — 2–3 дня)
1. **Git Smart HTTP (`/git/<repo>/*`)** в `src/direct.mjs` через системный `git http-backend` с Bearer-авторизацией, проверкой `protected`-путей и ограничением пуша только в безопасное пространство веток `refs/heads/agent/*` (настраиваемо).
2. **Раздача лёгкого CLI-клиента `GET /ab`** и обновление `src/prompt.mjs`, чтобы облачный агент за 1 секунду ставил `ab` в песочнице и получал удобные команды `ab repos`, `ab clone`, `ab batch`, `ab patch`, `ab exec`.
3. **Инструмент `apply_patch`** с валидацией путей через `checkPath` и атомарным применением через `git apply`.

### Фаза 3 — Изоляция рабочего процесса и страховка (Impact: High, Effort: M — 2–3 дня)
1. **Инструмент `git_worktree`** (`create` / `list` / `cleanup`) для параллельной сборки и тестов на вашем Mac без вмешательства в активную рабочую директорию.
2. **Невидимые страховочные снапшоты (`git stash create`)** перед первой мутацией грязного репозитория с сохранением SHA в запись `audit.log` и командой `arena-bridge restore <audit-id>`.
3. **Long-polling / WebSocket для Hub-режима** (`src/device.mjs`, `src/hub.mjs`) + проброс полного каталога инструментов устройства на хаб.

## 6. Инварианты безопасности (что остаётся незыблемым)

1. **Zero new dependencies**: никаких сторонних пакетов из npm — минимальная поверхность атаки и мгновенная установка.
2. **Единая граница `checkPath`**: и `apply_patch`, и `git http-backend`, и `code_search`, и `git_worktree` проходят через ту же самую проверку `protected`-путей (`~/.ssh`, `~/.aws`, `~/.arena-bridge`, `~/.git-credentials` и т.д.) и защиту от симлинков (`lstat`). Репозиторий внутри `protected` не может быть ни проиндексирован, ни склонирован.
3. **Никаких секретов в URL**: Git Smart HTTP использует заголовок `Authorization: Bearer <token>` через `http.extraHeader`, поэтому токен никогда не попадает ни в URL remote'ов (`.git/config`), ни в историю команд с открытым URL, ни в логи прокси.
4. **Неприкосновенность ветки человека**: по умолчанию прямой `git push` от агента в текущую checkout-ветку пользователя запрещён — агент пушит в `agent/*`, а слияние остаётся под полным контролем владельца машины (или явного поручения агенту).
